# 目的与迭代

## 核心原则

先理解用户真正想要什么，再决定流程。Harness 的目的不是执行一堆文档，而是持续接近可验证的用户结果。

## 目的澄清

开发前必须弄清：

- 用户要解决的问题是什么。
- 用户最终希望看到什么结果。
- 成功标准是什么。
- 哪些内容明确不做。
- 当前约束是什么。
- 需要先探索还是可以直接实现。

如果这些问题不清楚，不要直接进入 Graphify、OpenSpec、Spec-Kit、Task Queue 长跑或多代理流程。

## 用户也不清楚时

当用户说“我也说不清”“感觉不好用”“帮我优化”时，先给出可选方向：

- 性能：卡顿、加载慢、交互延迟。
- 交互：步骤绕、反馈弱、状态不清。
- 视觉：层级、布局、密度、可读性。
- 架构：难维护、耦合高、边界不清。
- bug：异常、测试失败、边界行为错误。
- 功能：缺少某个明确能力。

可以先做只读探索，再给出判断。探索不等于开工。

## 迭代校准

用户中途改变方向时：

1. 停下当前推断。
2. 判断是纠正目标、追加需求，还是排队后续任务。
3. 更新 `docs/agentic-dev/ACTIVE.md`、plan、tasks 或 handoff。
4. 如果新方向与旧目标冲突，先确认。
5. 如果用户要求“记录一下”或“以后按这个来”，按 `rules-and-memory.md` 的上下文同步协议判断是否同步到 `AGENTS.md` / `CLAUDE.md`。

不要继续执行旧方向来“完成计划”。计划服务于目的，不是目的本身。

## 目的优先的 skill routing

- “优化自由画布”：先澄清性能、交互、视觉、架构、bug 还是功能。
- “自由画布拖拽卡顿”：systematic-debugging + 性能验证，必要时 Graphify。
- “自由画布交互不好用”：ui-ux-pro-max + 浏览器验收。
- “重构画布架构”：Graphify + OpenSpec。
- “构建自由画布模块”：存量项目新增模块，OpenSpec 或任务目录。
- “新建画布应用”：greenfield，Spec-Kit。

## 写回规则

- 临时想法：写入当前 run 或 handoff。
- 当前目标状态：写入 `docs/agentic-dev/ACTIVE.md`。
- 当前计划与任务：写入 `docs/agentic-dev/TASKS.md`、`tasks/` 或 `handoff.md`。
- 稳定项目事实：写入 `memory/`。
- 稳定约束或工作方式：必要时写入 `AGENTS.md`。
- 未确认偏好或一次性想法：写入 `ACTIVE.md` 的待确认项。

不要把一次性偏好或未验证猜测写入规则层。
